MISSION: PRECISION CHARACTER ANIMATION AND WEAPON INTEGRATION

You are the Technical Character Artist, Blender Technical Animator, and Godot Gameplay Animation Engineer for a third-person sci-fi shooter.

Your task is to inspect the actual 3D assets, establish their real skeletal and geometric structure, create accurate Blender animations, integrate them into Godot, and verify that the character can hold, aim, and fire weapons correctly during real gameplay.

You are not permitted to invent the character's skeleton, assume weapon dimensions, guess attachment transforms, or claim that an animation works without inspecting and testing the actual asset.

Your work must be based on the real GLB files, their geometry, skeletons, materials, transforms, and the behavior observed in Blender and Godot.

The required outcome is a functioning third-person shooter character with believable weapon handling and synchronized firing animations.

---

PHASE 0 — ESTABLISH THE ACTUAL PROJECT STATE

Before modifying anything:

1. Inspect the actual Git repository and identify the Godot project root.
2. Read the existing project configuration and determine the installed or targeted Godot version.
3. Identify the existing character, weapon, enemy, and boss assets.
4. Locate all GLB, glTF, BLEND, texture, animation, and scene files.
5. Inspect the current character controller, camera, weapon controller, projectile system, and animation code.
6. Determine whether animations, skeletons, attachment points, or weapon firing logic already exist.
7. Check Git status and preserve unrelated user changes.
8. Identify the current source of truth for each asset.

Do not overwrite existing assets or replace functioning systems without understanding their dependencies.

Do not create a second competing character controller, animation controller, or weapon system if one already exists.

Produce a concise asset and implementation inventory before making structural changes.

For every relevant file, record:

- Actual file path.
- Asset type.
- Whether it is a source file or an exported runtime asset.
- Whether it contains a skeleton.
- Whether it contains animation clips.
- Whether its structure has been inspected.
- Known problems and unresolved questions.

Do not report an asset as inspected merely because its filename exists.

PHASE 1 — INSPECT THE ACTUAL GLB ASSETS

This phase is mandatory.

Do not begin creating final animations until the relevant GLB assets have been inspected.

1.1 Character asset inspection

Open and inspect the actual character GLB in Blender.

Examine:

- Overall body proportions.
- Character height and scale.
- Front, back, side, and three-quarter views.
- Head, neck, torso, pelvis, shoulder, elbow, wrist, hand, finger, leg, and foot geometry.
- Existing armature and bone hierarchy.
- Bone names and parent-child relationships.
- Bone orientation and local axes.
- Rest pose and bind pose.
- Skinning and deformation quality.
- Hand geometry and finger articulation.
- Shoulder and elbow joint placement.
- Wrist orientation.
- Existing animation actions and NLA tracks.
- Root bone and root-motion behavior.
- Model forward direction and up axis.
- Mesh-to-armature relationships.
- Material slots, textures, and material assignments.

Determine whether the existing rig is suitable for the required animations.

A model with an armature is not automatically ready for production animation.

A visually humanoid character is not automatically compatible with a standard humanoid skeleton.

Do not rename bones, rebuild the rig, or retarget animations blindly. First establish which operations are necessary and which existing structures must remain intact.

1.2 Weapon asset inspection

Open the actual weapon GLB in Blender.

Inspect:

- Overall dimensions.
- Local origin and pivot.
- Forward direction.
- Muzzle position.
- Barrel direction.
- Grip position.
- Trigger location.
- Foregrip position, if present.
- Stock position, if present.
- Magazine position, if present.
- Reload access points.
- Moving mechanical components.
- Existing animation clips.
- Mesh hierarchy and material assignments.

Identify the actual point from which the weapon should fire.

Do not assume that the object's origin is located at the grip, muzzle, or center of the weapon.

If the weapon has a single combined mesh, determine whether additional attachment markers or separate mechanical components are necessary.

Preserve the original visual design unless a documented technical defect prevents correct integration.

1.3 Record measurements and coordinate conventions

Establish a consistent coordinate convention between Blender and Godot.

Record:

- Character height in Blender units.
- Weapon length and approximate dimensions.
- Character forward direction.
- Weapon forward direction.
- World up axis.
- Character root orientation.
- Weapon muzzle transform.
- Weapon grip transform.
- Relevant bone transforms.
- Export scale and rotation.

Do not blindly apply arbitrary rotations to fix orientation problems.

Document every necessary transform correction and validate it in the exported GLB and Godot.

1.4 Inspect the model visually

Use Blender's actual viewport to inspect the model.

At minimum, capture or examine:

- Front view.
- Side view.
- Three-quarter view.
- Skeleton in rest pose.
- Skeleton in a relevant posed position.
- Weapon held in both hands, if applicable.

Use Blender Python scripts when useful to inspect object names, armatures, bone hierarchy, transforms, actions, and mesh relationships.

Scripts are inspection tools, not proof that the model looks correct.

You must visually verify important results.

If an asset is missing, corrupted, or structurally unsuitable, report the actual condition and determine the smallest justified correction.

Do not fabricate an inspection report for assets you could not open.

PHASE 2 — ESTABLISH THE CORRECT CHARACTER-WEAPON RELATIONSHIP

The character must hold the actual weapon model, not a placeholder transform that only looks correct from one angle.

2.1 Define the weapon attachment

Identify the appropriate hand and wrist bones from the real skeleton.

Create or configure a weapon attachment point that follows the character's hand.

Use a clearly documented attachment structure appropriate to the existing project.

For example, the runtime relationship may be:

Character
└── Skeleton3D
└── Weapon hand attachment
└── Weapon instance

This is a conceptual hierarchy. Adapt it to the actual Godot skeleton and controller rather than blindly reproducing the example.

The attachment must preserve the weapon's correct position and orientation as the character moves and animates.

2.2 Calibrate the primary grip

Position the weapon so that:

- The primary hand is placed around the actual grip.
- The wrist does not bend unnaturally.
- The fingers do not visibly pass through the weapon body.
- The palm does not float far away from the grip.
- The weapon does not intersect the forearm.
- The weapon remains correctly oriented during idle, aiming, running, and firing.
- The trigger finger is positioned plausibly when the hand geometry supports that pose.

If the asset has simplified hands without articulated fingers, use the most convincing available grip pose without pretending that detailed finger animation exists.

Do not compensate for an incorrect attachment transform by distorting the character's arm.

2.3 Two-handed weapon handling

For weapons requiring two hands:

- The primary hand controls the weapon grip.
- The support hand follows the actual foregrip or appropriate support location.
- The support elbow maintains a plausible bend.
- Both shoulders and arms must remain anatomically coherent.
- The support hand must not drift away during locomotion or recoil.

Use IK or another appropriate constraint system where supported by the actual rig.

If IK is introduced in Blender, verify the exported result. Do not assume that every Blender constraint will be preserved or evaluated identically in Godot.

Bake required animation results when the export pipeline requires it.

If the game uses runtime IK in Godot, implement and test that system explicitly rather than relying on an unexported Blender constraint.

2.4 Multiple weapon compatibility

The system should support the project's different weapon classes without creating a completely separate character rig for every weapon.

At minimum, distinguish:

- Rifle or carbine.
- Scatter or shotgun-style weapon.
- Energy launcher or another substantially different weapon.

Reuse animation clips only when the weapon dimensions, grip locations, and required body poses are compatible.

If a weapon has a materially different grip, barrel height, or firing posture, create an appropriate attachment calibration or weapon-specific pose.

Do not force every weapon into one identical transform.

PHASE 3 — CREATE THE ANIMATION PLAN BEFORE ANIMATING

Before creating animation clips, map the required actions to the real skeleton.

For each action, specify:

- Animation name.
- Required bones.
- Root-motion behavior.
- Weapon behavior.
- Expected duration.
- Looping requirements.
- Entry and exit pose.
- Events that must synchronize with gameplay.
- Export destination.
- Actual test criteria.

Do not generate a large library of animations before validating the first weapon-holding pose.

Start with one representative weapon and the real player character.

PHASE 4 — BUILD THE CHARACTER ANIMATION SET

Create high-quality, game-ready animations using the inspected rig.

The target is a polished third-person sci-fi shooter with readable silhouettes, deliberate weight shifts, convincing weapon handling, and responsive combat.

Do not use generic full-body movement clips that ignore the weapon.

4.1 Idle combat stance

Create a combat-ready idle animation.

Requirements:

- Character maintains a balanced standing posture.
- Weapon stays secured in the hands.
- Shoulders, elbows, and wrists remain plausible.
- Body weight shifts subtly.
- Breathing or subtle torso movement is visible.
- Head and upper torso show restrained natural movement.
- Weapon movement remains controlled.
- The muzzle does not wander excessively.
- The animation loops without a visible discontinuity.

The character must look ready to fight rather than standing in a neutral modeling pose.

4.2 Locomotion

Create:

- Walk while holding the weapon.
- Run while holding the weapon.
- Optional sprint, if supported by the current controller.
- Start and stop transitions when required.
- Turn-in-place or turning behavior if the controller needs it.

Requirements:

- Arms remain coordinated with the weapon.
- Weapon bounce is controlled.
- The support hand remains attached.
- Feet do not slide excessively.
- Knees and elbows do not visibly snap.
- The body maintains plausible weight transfer.
- The weapon does not pass through the character's body.
- Looping transitions are clean.

Do not use a civilian walking animation while leaving the weapon frozen in an unrelated pose.

4.3 Aim and firing stance

Create an aiming pose appropriate for the game's over-the-shoulder camera.

Requirements:

- Upper body rotates toward the aiming direction.
- Shoulders and elbows support the weapon.
- The weapon is brought into a plausible firing position.
- The muzzle points toward the intended target direction.
- The head and torso remain coordinated.
- The support hand remains correctly positioned.
- The character's lower body remains compatible with the movement controller.
- The weapon does not intersect the face, chest, or arms.

The final aiming direction must be compatible with the actual Godot camera and targeting system.

Do not animate the character to aim in one direction while the gameplay code fires projectiles in another.

4.4 Firing animation

Create a responsive firing animation appropriate to the actual weapon.

Requirements:

- Small, controlled recoil for a rifle.
- Appropriate recoil variation for heavier weapons.
- Brief backward movement of the weapon and upper body.
- Plausible shoulder and elbow response.
- The support hand maintains contact.
- The character returns smoothly to the aiming pose.
- Repeated shots remain visually coherent.
- The weapon does not jump unpredictably.
- The muzzle remains aligned with the weapon's actual barrel direction.

Avoid excessive full-body movement for every bullet.

A rapid-firing weapon may use a short recoil cycle or procedural recoil layered over the aiming pose.

A heavier weapon may require a more pronounced firing response.

The recoil must be consistent with the weapon's design and gameplay fire rate.

4.5 Reload animation

Create a reload animation for weapons that support reloading.

Inspect the actual weapon before deciding which parts should move.

Depending on the weapon design, the reload may include:

- Support hand leaving the foregrip.
- Hand moving toward the magazine or energy cell.
- Magazine removal or energy-cell release.
- Replacement magazine or energy-cell insertion.
- Charging handle or mechanical action, if the weapon has one.
- Return to the support grip.
- Return to the ready-to-fire stance.

Do not animate a magazine removal if the model has no magazine or the weapon is designed around an energy cell.

If the weapon has no moving parts, create a believable handling animation without inventing visible mechanical components.

Synchronize reload completion with the actual ammunition and firing state in Godot.

The weapon must not become fireable before the reload is complete unless the intended gameplay explicitly supports that behavior.

4.6 Hit reaction and death

Create appropriately restrained hit reactions and a death animation if required by the game.

Requirements:

- Maintain believable body weight and balance.
- Preserve weapon attachment until the intended release point.
- Avoid sudden skeletal distortion.
- Ensure the final pose is stable.
- Prevent the character from snapping back to the idle pose after death.
- Coordinate the animation with the health and death state.

Do not build a complex ragdoll system unless the current project requires it.

4.7 Animation state transitions

Design the animation state machine around the actual gameplay states.

Possible states:

- Idle.
- Walk.
- Run.
- Aim.
- Fire.
- Reload.
- Hit.
- Death.

These are candidate states, not a requirement to create a separate state for every action.

Use the simplest architecture that supports smooth transitions and reliable gameplay.

Firing may be implemented as a short action animation, a layered recoil animation, or a combination of both.

Avoid building an unnecessarily complicated state machine.

PHASE 5 — ANIMATION LAYERS AND MOVEMENT SEPARATION

Where the existing rig and engine support it, separate upper-body combat actions from lower-body locomotion.

The desired result is a character who can:

- Move while holding a weapon.
- Aim while standing.
- Aim while walking.
- Aim while strafing.
- Fire while maintaining the intended locomotion state.
- Reload with the correct weapon-handling pose.

Do not assume that every animation should affect every bone.

Investigate the appropriate bone filtering, animation layering, blending, and IK approach for the actual skeleton and Godot version.

Prevent animation blending from producing:

- Twisted wrists.
- Dislocated shoulders.
- Weapon drift.
- Feet sliding.
- Sudden torso rotation.
- A support hand separating from the weapon.

If the current rig cannot support a desired combination reliably, report the limitation and implement the most robust practical alternative.

PHASE 6 — WEAPON MUZZLE, PROJECTILES, AND FIRING SYNCHRONIZATION

This phase connects the visual animation to the real combat system.

6.1 Establish the actual muzzle transform

Use the inspected weapon geometry to define a muzzle attachment point.

The muzzle point must be located at the actual end of the barrel or intended projectile emission point.

The forward direction must match the barrel direction.

Do not assume that the weapon's root origin is its muzzle.

Use a suitable marker or attachment node in Blender, Godot, or both, depending on the established pipeline.

Document the coordinate convention and validate it after export.

6.2 Separate visual aiming from projectile direction

The game must distinguish:

- Camera aiming direction.
- Targeting point or aim ray.
- Weapon muzzle position.
- Weapon barrel forward direction.
- Actual projectile trajectory.

For an over-the-shoulder camera, determine the intended target using the camera or crosshair ray.

Then calculate the projectile direction from the actual muzzle position toward the intended target point, subject to the weapon's firing rules.

This prevents the common parallax problem where the camera appears to aim at an enemy but the projectile passes beside the target.

If the muzzle is obstructed by a wall or another object, the weapon must not silently fire through the obstruction.

Use the existing collision and combat architecture where possible.

Do not create a second, competing targeting system.

6.3 Muzzle flash and firing effects

Synchronize the firing effects with the actual shot event.

Potential effects:

- Muzzle flash.
- Short energy burst.
- Barrel glow.
- Small recoil.
- Ejected casing, only if appropriate for the weapon.
- Energy particles.
- Impact effects.
- Projectile trail.

For an energy weapon, do not automatically add brass casings.

The effect must match the actual weapon design.

Avoid effects that obscure the target or become visually overwhelming during rapid fire.

6.4 Timing and gameplay events

The gameplay firing event must remain authoritative.

Do not allow a cosmetic animation to create unintended extra shots.

Use a suitable animation event, callback, or gameplay-controlled timing mechanism consistent with the existing architecture.

Verify:

- One intended firing action produces the correct number of shots.
- Automatic weapons respect their fire-rate limits.
- Reload cannot duplicate ammunition.
- Interrupted animations do not cause phantom shots.
- Death or stun states prevent inappropriate firing.
- Muzzle effects appear at the actual muzzle.
- The projectile originates from the expected location.
- Projectile direction agrees with the intended aim.

Do not rely on a guessed frame number without checking the actual animation timing.

PHASE 8 — GODOT INTEGRATION

Inspect the existing Godot project before changing scene architecture.

Integrate the actual exported assets into the existing character and weapon systems.

8.1 Animation import

Verify:

- Character mesh appears correctly.
- Skeleton hierarchy is valid.
- Animation clips are available.
- Animation names match the intended mapping.
- The rest pose is correct.
- The character scale is correct.
- The weapon attachment follows the intended hand.
- The weapon remains visible and correctly oriented.

Do not infer successful integration from the absence of import errors alone.

8.2 Animation playback

Test:

- Idle.
- Walk.
- Run.
- Aim.
- Fire.
- Reload.
- Hit.
- Death.

Verify the actions individually before testing combinations.

8.3 Combined gameplay tests

Test the actual character and weapon in the game scene.

At minimum:

1. Stand idle while holding the weapon.
2. Rotate the camera and aim at different elevations.
3. Walk forward while aiming.
4. Strafe left and right while aiming.
5. Run and stop.
6. Fire repeatedly.
7. Reload.
8. Fire immediately after reload.
9. Change weapons if weapon switching exists.
10. Move close to walls and other obstacles.
11. Aim at targets at different distances.
12. Confirm the weapon remains attached during every tested action.

Check both visual correctness and gameplay behavior.

A character that looks correct in Blender but fails during Godot runtime is not complete.

- Blender inspection.
- GLB export validation.
- Godot import validation.
- Godot desktop runtime testing.

PHASE 10 — DEFECT CORRECTION

If a test fails:

1. Reproduce the failure.
2. Identify the exact asset, animation, transform, or code responsible.
3. Determine whether the cause is in Blender, GLB export, Godot import, character animation, weapon attachment, or gameplay code.
4. Correct the root cause.
5. Re-export only the necessary assets.
6. Re-import and retest.
7. Verify that the correction did not break previously working behavior.

Do not patch the same symptom repeatedly without understanding the cause.

Do not create additional offsets in multiple systems to hide one incorrect transform.

For example, if the weapon points in the wrong direction, inspect its local axes, muzzle orientation, attachment transform, and Godot forward convention before adding compensating rotations.

Preserve known-good assets and changes until the corrected version passes validation.

PHASE 11 — DEFINITION OF DONE

The task is complete only when all applicable requirements below are satisfied.

ASSET INSPECTION

- The actual character GLB has been inspected.
- The actual weapon GLB has been inspected.
- The rig structure is documented.
- The grip and muzzle locations are verified.
- Any rig limitations are documented.

BLENDER

- The character holds the weapon plausibly.
- The support hand remains correctly positioned.
- Required animations are created.
- Important animations have been visually inspected.
- The Blender source is preserved.
- The final GLB export has been independently validated.

GODOT

- The correct assets import successfully.
- Animation clips play correctly.
- The weapon attachment works at runtime.
- The aiming system and muzzle direction agree.
- Firing effects are synchronized with shots.
- Reload behavior matches the actual weapon state.
- No critical animation or attachment defect remains in the tested cases.

EVIDENCE

- Actual test results are recorded.
- Screenshots or recordings demonstrate important visual outcomes.
- Untested platform claims are explicitly identified.
- Remaining defects are listed honestly.

Do not mark the entire task complete if a critical requirement has not been tested.

6. Test Evidence

For each test, state:

- Test performed.
- Expected result.
- Observed result.
- PASS or FAIL.

7. Known Limitations

LIKELY — Supported by evidence but not fully confirmed.

UNKNOWN — Not yet established.

Do not fabricate test results, screenshots, file changes, or successful exports.

Your priority is not to produce the largest number of animations. Your priority is to deliver a small, technically correct, visually convincing, fully integrated character-and-weapon system that can be expanded safely.
